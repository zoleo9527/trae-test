# 高尔夫练习场会员储值与消耗对账系统 - 实现取舍点与后续扩展说明

## 一、当前实现取舍点

### 1. 技术栈选型

#### 1.1 数据库选型：SQLite
**取舍原因：**
- 项目定位为单机场馆系统，SQLite 足够支撑 10 万级数据量
- 零配置、零运维，无需额外安装数据库服务
- 单文件存储，备份迁移简单
- 更好-sqlite3 同步 API 性能优秀，避免回调地狱

**局限性：**
- 不支持并发写入（虽然通过事务可以缓解）
- 不支持分布式部署
- 未来多场馆扩展时需要迁移到 PostgreSQL/MySQL

**迁移成本：** 低。数据访问层集中在 `server/src/models/`，替换数据库驱动即可。

---

#### 1.2 认证方案：JWT
**取舍原因：**
- 无状态，服务端不需要存储会话
- 前后端分离架构下实现简单
- 支持多端共享（未来扩展小程序/App）

**局限性：**
- Token 一旦签发无法主动撤销（除非引入黑名单机制）
- Token 过期时间需要权衡安全性和用户体验

**当前配置：**
- Token 有效期 2 小时
- 前端拦截器自动处理 401 跳转到登录页

---

#### 1.3 前端状态管理：Zustand
**取舍原因：**
- 相比 Redux 代码量减少 70%
- API 简单直观，学习成本低
- 内置 persist 中间件支持本地持久化
- 对 TypeScript 支持友好

**局限性：**
- 缺少 Redux DevTools 那样强大的时间旅行调试
- 大型应用可能需要额外的架构规范

---

### 2. 功能实现取舍

#### 2.1 角色权限模型：简单 RBAC
**取舍原因：**
- 当前只有 3 种角色，简单的路由级别校验足够
- 实现简单，性能开销小

**当前权限矩阵：**

| 功能 | 场馆经理 | 教练主管 | 前台 |
|------|----------|----------|------|
| 数据概览 | ✅ | ✅ | ❌ |
| 前台工作台 | ✅ | ❌ | ✅ |
| 教练工作台 | ✅ | ✅ | ❌ |
| 对账中心 | ✅ | ❌ | ❌ |
| 异常处理 | ✅ | ❌ | ❌ |
| 操作日志 | ✅ | ❌ | ❌ |
| 口径配置 | ✅ | ❌ | ❌ |
| 会员详情 | ✅ | ✅ | ✅ |
| 储值充值 | ✅ | ❌ | ✅ |

**未来扩展：** 可以升级为完整的 RBAC，支持角色自定义、菜单级权限、按钮级权限。

---

#### 2.2 多条件筛选：后端动态 SQL 构建
**取舍原因：**
- 使用 `buildWhereClause` 工具函数统一处理筛选条件
- 自动防 SQL 注入（使用参数化查询）
- 支持 `_start`/`_end`/`_min`/`_max`/`_like` 后缀约定

**当前支持的筛选类型：**
- 文本模糊搜索 (`_like`)
- 日期范围 (`_start`, `_end`)
- 数值范围 (`_min`, `_max`)
- 精确匹配
- 多选 IN 查询

**局限性：**
- 复杂的 OR 条件需要额外处理
- 关联表筛选需要特殊处理

---

#### 2.3 操作留痕：统一日志中间件
**取舍原因：**
- 在 Service 层调用 `logAudit` 记录操作
- 记录操作前后数据对比（JSON 格式）
- 支持按模块、操作人、时间范围多维度回查

**记录的关键操作：**
| 模块 | 操作 | 记录内容 |
|------|------|----------|
| 认证 | 登录/登出 | IP、User-Agent、时间 |
| 会员 | 新增 | 完整会员信息 |
| 储值 | 充值/扣减 | 余额变更前后、金额明细 |
| 预约 | 创建/签到/完成 | 状态变更前后 |
| 器材 | 借出/归还 | 库存变化、损坏记录 |
| 对账 | 审核/调账 | 调账金额、原因、审批人 |
| 异常 | 创建/处理 | 处理结果、关联数据 |
| 配置 | 更新 | 配置变更前后对比 |

**局限性：**
- 查询变更前后的差异需要额外查询一次数据库，有一定性能开销
- 二进制数据（图片）不记录具体内容，只记录引用

---

#### 2.4 储值账户设计：本金/赠送金分离
**取舍原因：**
- 赠送金有不同的有效期和使用规则
- 扣减优先级可配置（先赠后金 vs 先金后赠）
- 对账时可以分别统计本金和赠送金的流动

**当前扣减口径：**
- 默认先扣赠送金，再扣本金（可在口径配置中修改）
- 每笔消费分别记录本金扣减额和赠送金扣减额
- 支持节假日和周末费率系数

**会计恒等式校验：**
```
储值充值(本金) - 消费扣减(本金) = 当前本金余额
储值充值(赠送金) - 消费扣减(赠送金) = 当前赠送金余额
```

---

#### 2.5 对账流程：日终人工审核
**取舍原因：**
- 场馆规模不大，日对账在可接受范围内
- 人工审核可以处理一些系统无法判断的边缘情况
- 自动生成对账数据 + 人工确认 = 效率与准确性的平衡

**当前对账流程：**
1. 点击"生成对账"按钮，系统自动汇总当日流水
2. 计算：充值总额 vs 消费总额 vs 现金应收
3. 标记异常（不匹配）的交易
4. 场馆经理审核，可逐笔调账
5. 审核通过后锁定对账数据

**未来可优化：**
- 定时任务自动生成对账
- 异常交易智能识别（金额偏差大、操作时间异常等）
- 支持周/月/季度对账

---

### 3. UI/UX 取舍

#### 3.1 设计风格：专业稳重风
**取舍原因：**
- 目标用户是场馆从业者，需要专业、可信赖的感觉
- 深绿色主色调呼应高尔夫运动属性
- 香槟金点缀体现高端感

**关键设计决策：**
- 字体：标题用 Noto Serif SC（稳重），正文用 Noto Sans SC（易读）
- 动效克制：只在状态变化、筛选操作时有过渡动画
- 表格优先：数据展示是核心，表格交互做扎实（排序、固定列、斑马纹、行高亮）

---

#### 3.2 响应式策略：桌面优先
**取舍原因：**
- 核心使用场景：前台 PC、经理办公室 PC
- 操作需要精确的鼠标交互和大表格展示
- 暂不支持移动端，减少开发复杂度

## 三、当前已知问题与改进计划

### 3.1 已知问题
1. **并发预约校验**：当前在应用层校验球道占用，高并发下可能出现超卖
   - 改进：数据库层面增加唯一索引 `(bay_id, booking_date, start_time)`

2. **余额扣减原子性**：当前用事务保证，但可进一步优化
   - 改进：使用 `UPDATE ... WHERE balance >= amount` 原子扣减

3. **图片证据存储**：当前只存储路径，不存储实际文件
   - 改进：集成 OSS/S3 存储截图证据

## 五、样例场景说明

### 5.1 正常流场景
**会员陈建国（钻石会员，ID=1）到店打球：**
1. 前台搜索"陈建国"，查看余额：本金 50,000 + 赠送金 5,000
2. 预约 20 号 VIP 球道，2 小时，费率 150 元/小时 × 2 = 600 元
3. 签到时自动扣减：赠送金 600 元（优先级配置为先扣赠送金）
4. 借出 1 号木杆（Titleist 9.5°）
5. 打完 2 小时后归还球杆，检查正常无损坏
6. 日终对账：该笔消费自动匹配，对账通过

**涉及数据：**
- 预约记录：ID = 1, 4, 8
- 交易流水：充值 ID = 1-5，消费 ID = 6-13
- 器材借还：ID = 1, 2

### 5.2 问题流场景 1：消费争议
**会员郑小刚（普通会员，ID=8）投诉：**
- 问题：昨日打球系统扣减 160 元，但实际只打了 1 小时应扣 80 元
- 系统操作：
  1. 前台创建异常工单（ID = 1），关联交易 ID = 12
  2. 场馆经理打开工单，查看郑小刚的全链路时间线
  3. 核实为前台操作失误，调账 +80 元
  4. 记录处理结果，操作留痕
  5. 该笔交易标记为"已调账"

**涉及数据：**
- 异常工单：ID = 1（状态：处理中）
- 关联交易：ID = 12
- 关联预约：ID = 5

### 5.3 问题流场景 2：器材损坏
**会员冯雅婷（银卡会员，ID=9）归还球杆：**
- 问题：归还一号木杆时发现杆头有划痕
- 系统操作：
  1. 前台登记损坏，选择"损坏归还"状态
  2. 填写损坏备注："杆头底部 3cm 划痕，疑似击球碰到硬物"
  3. 录入损坏赔偿费：500 元
  4. 系统自动从储值账户扣减 500 元本金
  5. 创建异常工单（ID = 2），标记器材损坏
  6. 库存：可用数量不变（损坏后仍可维修再用）

**涉及数据：**
- 异常工单：ID = 2（状态：待处理）
- 器材记录：ID = 3
- 关联预约：ID = 7

### 5.4 问题流场景 3：预约冲突（已解决）
**会员孙晓峰（银卡会员，ID=5）投诉：**
- 问题：15:00 的球道被安排给了其他客人，等待 30 分钟
- 处理结果：核实为前台操作失误，赠送 200 元储值作为补偿
- 当前状态：已解决（ID = 3）

**涉及数据：**
- 异常工单：ID = 3（状态：已解决）
- 关联预约：ID = 6
