# ⚠️ 乐器租赁系统 - 边界说明

本文档说明当前系统版本中**做了轻量化处理**的功能边界，以及设计时的权衡考量和后续迭代建议。

---

## 🎯 设计原则

当前版本遵循 **"核心链路完整，非核心轻量化"** 的原则：
- ✅ **做厚**：押金结算、损坏申诉、状态流转、审计追踪、权限控制
- ⚖️ **做薄**：支付对接、文件存储、消息通知、报表统计
- ❌ **不做**：前端界面、多门店管理、复杂财务对账

---

## 📋 已轻量化处理的功能清单

### 1. 💰 支付系统 - 状态模拟

**当前实现**：
- 押金结算仅更新数据库状态（`REFUNDED` / `DEDUCTED` / `PARTIAL_REFUNDED`）
- 没有对接真实支付网关（微信、支付宝、银行）
- 没有实际资金流转

**数据模型中的占位字段**：
```prisma
model Deposit {
  // ...
  paymentMethod  String?  // 支付方式（仅记录，未对接）
  transactionId  String?  // 支付流水号（仅记录，未对接）
}
```

**后续迭代建议**：
- 接入支付网关 SDK（微信支付 v3、支付宝）
- 增加支付回调处理接口
- 增加资金对账模块
- 支持退款申请的人工审核

---

### 2. 📷 文件存储 - URL 占位

**当前实现**：
- 损坏照片仅存储 URL 字符串（如 `photo1.jpg, photo2.jpg`）
- 没有文件上传接口
- 没有实际文件存储（本地磁盘 / OSS / 七牛云等）

**数据模型中的占位字段**：
```prisma
model DamageClaim {
  // ...
  evidencePhotos String?  // 照片URL，逗号分隔
}
```

**后续迭代建议**：
- 增加 `POST /api/upload` 文件上传接口
- 支持图片压缩和格式校验
- 接入对象存储服务（阿里云 OSS / 腾讯云 COS）
- 增加照片水印功能（时间、地点、拍摄人）

---

### 3. 🔔 消息通知 - 接口预留

**当前实现**：
- 没有实现真实的消息推送（短信 / 邮件 / 微信 / 站内信）
- 所有"提醒"功能都通过状态变化和审计日志隐式体现
- 没有通知模板管理

**设计权衡**：
> 通知系统依赖第三方服务（短信网关、邮件服务器、企业微信等），且每个门店的通知渠道偏好不同。当前版本通过完整的审计日志和状态追踪，保证"发生了什么、谁操作的、什么时候"可追溯，通知功能作为后续迭代。

**后续迭代建议**：
- 增加 `Notification` 数据模型
- 接入短信网关（阿里云短信 / 腾讯云短信）
- 支持邮件通知（Nodemailer）
- 支持企业微信 / 钉钉 Webhook 通知
- 增加通知模板管理和发送记录

---

### 4. 🏫 学校合作回款 - 标记简化

**当前实现**：
- 仅在租赁单上增加 `isSchoolCooperation` 布尔标记
- 没有学校对账周期、回款计划、分期收款等功能
- 没有逾期罚息计算

**数据模型中的占位字段**：
```prisma
model Rental {
  // ...
  isSchoolCooperation Boolean  @default(false)
  schoolContractNo    String?  // 学校合同编号（仅记录）
}
```

**设计权衡**：
> 学校合作的财务流程差异极大（月结 / 季度结 / 学期结 / 按课时结算），且涉及对公转账、发票开具等复杂流程。当前版本先保证能"识别"哪些是学校合作单，完整的财务对账作为后续迭代。

**后续迭代建议**：
- 增加 `SchoolContract` 模型（合同、账期、回款计划）
- 增加 `Invoice` 模型（发票管理）
- 增加回款提醒和逾期罚息计算
- 支持批量结算和批量开票

---

### 5. 📊 报表统计 - 基础汇总

**当前实现**：
- 仅提供维修费用汇总接口 `GET /api/maintenances/summary`
- 没有复杂的多维度报表
- 没有数据导出功能（Excel / PDF）

**已有的基础统计**：
- 维修费用按时间段汇总
- 按乐器统计维修次数

**后续迭代建议**：
- 租赁报表：出租率、逾期率、热门乐器排行
- 财务报表：押金流水、损坏赔偿、维修成本
- 客户报表：租赁频次、欠款统计
- 支持 Excel / PDF 导出
- 支持自定义时间段和筛选条件

---

### 6. 🖥️ 前端界面 - 纯 API 服务

**当前实现**：
- 仅提供 RESTful API 服务层
- 没有 Web 前端、小程序、桌面端
- 没有可视化的操作界面

**设计权衡**：
> 按用户需求，当前版本优先保证"能直接被前端或桌面端接住的服务层"，界面层由前端团队对接。API 设计已考虑前端对接体验（统一响应格式、清晰的错误码、完整的类型定义）。

**后续迭代建议**：
- 管理后台 Web 端（React / Vue）
- 移动端小程序（客户查询、扫码还琴）
- 桌面端（门店收银、快速开单）
- 数据大屏（门店运营看板）

---

### 7. 🏪 多门店支持 - 数据模型预留

**当前实现**：
- 所有数据默认属于单个门店
- 没有门店切换、门店数据隔离
- 没有区域管理、连锁总部视图

**数据模型中的占位字段**：
```prisma
model User {
  // ...
  storeId String?  // 门店ID（预留，当前未使用）
}

model Instrument {
  // ...
  storeId String?  // 门店ID（预留，当前未使用）
}
```

**后续迭代建议**：
- 增加 `Store` 模型
- 所有业务数据增加 `storeId` 维度
- 增加"总部管理员"角色，可查看全部门店数据
- 支持门店间乐器调拨

---

### 8. 🔒 数据级权限 - 角色级简化

**当前实现**：
- 权限控制是**角色级**的（如"顾问可以看所有租赁单"）
- 没有**数据级**权限（如"顾问只能看自己创建的租赁单"）
- 没有部门、小组等组织架构维度

**已有的权限控制**：
```typescript
// 角色级权限
export const rolePermissions: Record<Role, string[]> = {
  [Role.RENTAL_ADVISOR]: ['rental:read', 'rental:create', ...],
}
```

**后续迭代建议**：
- 增加组织架构模型（部门、小组）
- 支持"只能看自己的数据"、"只能看本部门数据"
- 支持自定义角色和自定义权限组合
- 增加权限申请和审批流程

---

### 9. ⚡ 并发控制 - 基础事务保障

**当前实现**：
- 使用数据库事务保证数据一致性
- 没有乐观锁、悲观锁等并发控制
- 没有操作前的状态二次校验

**已有的并发保障**：
- 所有写操作使用 `prisma.$transaction`
- 状态变更前校验前置状态
- 幂等性键防止重复提交

**后续迭代建议**：
- 增加 `version` 字段实现乐观锁
- 关键操作增加状态二次校验（数据库层面）
- 增加分布式锁（Redis）
- 支持操作冲突提示和人工干预

---

### 10. 💾 数据备份 - 手动操作

**当前实现**：
- 没有自动数据备份机制
- 没有增量备份、异地备份
- 没有数据恢复工具

**设计权衡**：
> SQLite 数据库本身就是一个文件，手动备份（复制文件）足够满足开发和演示需求。生产环境建议切换到 PostgreSQL 并配置专业的备份策略。

**后续迭代建议**：
- 定时自动备份（cron job）
- 增量备份和恢复点管理
- 异地备份（云存储）
- 一键数据恢复工具

---

## 🚧 已知的功能限制

### 1. 客户管理简化
- 没有客户等级、积分、会员卡
- 没有客户联系方式的完整性校验
- 没有客户租赁历史画像

### 2. 乐器库存管理简化
- 没有库存预警（维修中、已租出、可租出数量统计）
- 没有乐器保养计划和提醒
- 没有折旧计算和残值管理

### 3. 优惠券 / 折扣简化
- 没有优惠券模型
- 没有折扣审批流程
- 没有价格策略配置

### 4. 操作日志查询简化
- 审计日志仅支持按实体查询
- 没有复杂的筛选条件（操作者、时间范围、操作类型组合）
- 没有操作日志导出

## 🎯 验收标准说明

当前版本已满足以下核心验收标准：

✅ **业务链路完整**：租出 → 归还 → 损坏申诉 → 判责 → 结算 → 维修，全链路打通

✅ **多角色协作**：老板、顾问、师傅三种角色权限清晰，边界明确

✅ **证据链可追溯**：每个关键动作的前后值、操作者、时间点都有审计日志

✅ **异常处理覆盖**：损坏争议、押金争议、驳回申诉、补录备注等异常场景都有处理

✅ **非功能需求**：日志、幂等、权限、事务，都有实现

❌ **非核心轻量化**：支付、文件、通知、报表，已按上述说明做轻量化处理
