# 商用清洁耗材申领与补货预警系统 - 实现说明

## 一、项目概述

本系统旨在解决商用清洁业务中**耗材申领、补货预警、排班打卡、质检整改**等业务流程分散、重复录入、提醒弱、历史难找等痛点。通过**联动日历视图**将各业务模块整合，实现从"发生"到"处理"的全流程追踪。

## 二、技术栈选型

### 2.1 核心技术栈
| 技术 | 版本 | 选型理由 |
|------|------|---------|
| Nuxt 3 | 3.11.x | SSR/SSG 支持，SEO 友好，自动路由，服务端渲染提升首屏性能 |
| Vue 3 | 3.4.x | Composition API，更好的 TypeScript 支持，性能更优 |
| TypeScript | 5.4.x | 类型安全，减少运行时错误，提升代码可维护性 |
| Pinia | 2.1.x | Vue 官方推荐状态管理，模块化设计，更好的 TypeScript 支持 |
| Tailwind CSS | 6.12.x | 原子化 CSS，开发效率高，一致性好，包体积可控 |
| Day.js | 1.11.x | 轻量级日期处理库，API 友好，支持中文本地化 |
| VueUse | 10.9.x | 组合式工具函数集，减少重复代码 |

### 2.2 技术取舍分析

#### ✅ 选择 Nuxt 3 而非纯 Vue 3
- **收益**：
  - 自动路由配置，无需手动管理路由表
  - 服务端渲染提升首屏加载速度和 SEO
  - 内置布局系统，便于多角色权限控制
  - 更好的开发体验（HMR、自动导入等）
- **代价**：
  - 学习曲线更陡，需理解 Nuxt 生命周期
  - 部署相对复杂，需 Node.js 环境
  - 部分第三方库需额外处理 SSR 兼容

#### ✅ 选择 Pinia 而非 Vuex
- **收益**：
  - 更简洁的 API，减少样板代码
  - 原生 TypeScript 支持，无需额外类型声明
  - 模块化设计，便于按业务领域拆分 store
  - DevTools 支持更好
- **代价**：
  - 生态相对 Vuex 稍小（但已足够成熟）
  - 没有 mutations 概念，需自行约定状态更新规范

#### ✅ 选择 Tailwind CSS 而非 UI 组件库
- **收益**：
  - 完全自定义设计，不受组件库样式约束
  - 按需生成，生产包体积小
  - 开发效率高，无需在 HTML 和 CSS 文件间切换
  - 响应式设计开箱即用
- **代价**：
  - 模板中 class 较多，可读性稍差
  - 需自行封装常用组件（按钮、卡片等）
  - 没有开箱即用的复杂组件（如 DatePicker）

#### ⚠️ 前端模拟数据而非真实后端
- **当前方案**：使用 TypeScript 定义完整数据模型，通过 mock 数据文件模拟后端 API
- **收益**：
  - 前端开发不依赖后端进度
  - 便于演示和测试各种业务场景
  - 数据结构清晰，为后端开发提供参考
- **待改进**：
  - 无持久化存储，刷新页面数据重置
  - 无真实的网络请求和错误处理
  - 不支持多用户并发

## 三、核心业务流程设计

### 3.1 耗材申领与补货预警流程
```
库存监控 → 库存低于警戒线 → 自动触发库存预警
                    ↓
项目主管收到预警 → 快速补货 → 创建申领单
                    ↓
申领单提交 → 待审核 → 项目主管审批 → 批准/拒绝
                    ↓（批准）
                  已发货 → 更新库存 → 解除预警
                    ↓
                 已完成 ← 确认收货
```

**关键联动设计**：
1. 申领单"已发货"状态触发库存自动更新
2. 库存更新后自动检查是否仍低于警戒线，决定是否解除预警
3. 预警处理记录与申领单关联，形成完整追踪链路

### 3.2 排班打卡异常处理流程
```
排班创建 → 员工打卡 → 系统自动判断打卡状态
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
      正常         异常       未打卡
        ↓           ↓           ↓
      记录       标记异常    触发漏打卡预警
                    ↓           ↓
                记录归档    项目主管处理
                                ↓
                          联系员工核实
                                ↓
                          人工补卡/记旷工
                                ↓
                          预警标记已解决
```

### 3.3 质检整改追踪流程
```
质检员创建质检记录 → 系统自动计算评分
                    ↓
        ┌───────────┼───────────┐
        ↓           ↓           ↓
    优秀/良好      合格        不合格
        ↓           ↓           ↓
      归档        归档      生成整改任务
                                ↓
                          分配整改负责人
                                ↓
                          触发整改预警
                                ↓
                          整改人员逐项完成
                                ↓
                          上传整改照片
                                ↓
                          质检员复查确认
                                ↓
                    ┌───────────┼───────────┐
                    ↓                       ↓
                  通过                   重新整改
                    ↓                       ↓
                解除预警                 重新分配
```

## 四、数据模型设计

### 4.1 核心实体关系
```
Project（项目）
    ├─→ Schedule（排班） 1:N
    │     └─→ PunchRecord（打卡记录） 1:1
    ├─→ QualityInspection（质检记录） 1:N
    │     └─→ RectificationRecord（整改记录） 1:1
    │           └─→ RectificationItem（整改项） 1:N
    └─→ SupplyRequisition（耗材申领单） 1:N
          └─→ RequisitionItem（申领明细） 1:N

Supply（耗材库存）
    └─→ 关联 RequisitionItem

Alert（预警）
    ├─→ 关联 PunchRecord（漏打卡）
    ├─→ 关联 RectificationRecord（整改）
    ├─→ 关联 Supply（库存）
    ├─→ 关联 Project（合同到期）
    └─→ 关联 SupplyRequisition（任务逾期）
```

### 4.2 关键设计决策

#### ✅ 预警系统独立设计
- 将预警作为独立实体，通过 `relatedType` 和 `relatedId` 关联不同业务对象
- 支持完整的状态流转历史（open → in_progress → resolved）
- 可扩展支持更多预警类型，无需修改核心数据模型

#### ✅ 状态机设计
各业务对象都有清晰的状态流转：
- 申领单：`draft` → `pending` → `approved`/`rejected` → `delivered` → `completed`
- 整改：`pending` → `in_progress` → `completed`/`overdue`
- 预警：`open` → `in_progress` → `resolved`

#### ⚠️ 多对多关系简化
- 当前实现中，员工与项目的多对多关系通过 `assignedStaff` 数组简化实现
- 优点：查询简单，开发效率高
- 缺点：不便于复杂查询，后续如需统计员工在多个项目的工时，需重构为关联表

## 五、角色权限设计

### 5.1 角色入口划分

| 角色 | 主要职责 | 菜单入口 |
|------|---------|---------|
| **项目主管** | 全局管控、审批决策、异常处理 | 仪表盘、日历视图、排班管理、耗材管理、质检管理、预警中心、历史记录 |
| **排班专员** | 排班创建、打卡管理、人员调度 | 仪表盘、日历视图、排班管理、打卡管理、预警中心 |
| **质检员** | 质量检查、整改追踪、复查确认 | 仪表盘、日历视图、质检管理、整改追踪、预警中心 |

### 5.2 权限控制实现
- **前端控制**：通过 `useAuthStore` 的 `hasPermission` 方法控制菜单和按钮显示
- **数据隔离**：不同角色看到的数据范围不同（Todo：当前为演示目的未做严格数据隔离）
- **操作控制**：敏感操作（如审批、删除）需验证角色权限

### ⚠️ 权限设计取舍
- 当前仅做前端权限控制，真实环境需后端二次验证
- 角色定义较粗，后续可细化为更细粒度的权限点
- 未实现数据范围权限（如项目主管只能看自己负责的项目）

## 六、日历联动视图设计

### 6.1 多维度事件整合
日历视图统一展示四类业务事件，通过颜色区分：
- 🔵 **排班事件**：蓝色系，显示员工、项目、时间段
- 🔴 **打卡异常**：红色/黄色系，显示缺勤、迟到、早退
- 🟢 **质检事件**：绿色系，显示评分和评价
- 🟣 **耗材申领**：紫色系，显示申领项目和数量

### 6.2 交互设计
```
月视图 → 点击日期 → 日视图 + 详情面板
  ↑                         ↓
切换视图模式          点击事件 → 关联业务详情
  ↓
周视图 → 拖拽员工 → 创建排班
```

### ✅ 性能优化点
1. **按需加载**：根据当前视图日期范围动态计算事件，避免全量计算
2. **虚拟滚动**：事件列表较多时启用虚拟滚动（Todo）
3. **计算属性缓存**：使用 Vue 计算属性缓存筛选后的事件列表
4. **防抖处理**：搜索和筛选输入添加 300ms 防抖

## 九、实现取舍点总结

### 9.1 已做的权衡

| 决策 | 收益 | 代价 | 适用场景 |
|------|-----|-----|---------|
| 前端模拟数据 | 开发快，演示方便 | 无持久化，无真实网络 | MVP 演示、需求验证 |
| 单 store 管理所有数据 | 简单直接，便于联动 | store 体积大，可测试性稍差 | 中小规模应用 |
| Tailwind 原子化 CSS | 开发效率高，一致性好 | 模板 class 多，可读性稍差 | 快速迭代的项目 |
| 粗粒度角色权限 | 实现简单，易于理解 | 灵活性不足 | 角色固定的业务系统 |
| 日历为主的交互 | 直观，业务连续性好 | 数据量大时可能拥挤 | 排班/预约类业务 |

### 9.2 刻意简化的部分

1. **持久化存储**：当前使用内存存储，未接入本地存储或后端
2. **网络请求**：未实现真实的 API 调用和错误处理
3. **表单验证**：仅做了基础的必填验证，未引入专业验证库
4. **图片上传**：使用随机图片模拟，未实现真实上传
5. **导出功能**：仅预留 UI，未实现真实导出
6. **通知推送**：仅前端弹窗提醒，未集成真实消息推送
7. **数据加密**：敏感数据（手机号）仅做简单脱敏显示
