# 🏠 家具展厅样品借出与归还管理系统

针对家具展厅样品借出管理混乱、数据分散、责任不清的痛点，基于**多人协作**设计的样品全生命周期管理系统。

## ✨ 核心特性

### 🎯 角色驱动的协作流程
- **展厅经理 (SHOWROOM_MANAGER)**：审批借出申请、验收归还样品、查看全部数据、审计追溯
- **销售顾问 (SALES_CONSULTANT)**：创建借出申请、确认样品借出、提交归还
- **安装协调 (INSTALL_COORDINATOR)**：协助样品验收、参与回查处理

### 🔍 首页一眼可见
- 待审批、待验收、需回查、已驳回、超时提醒的统计卡片
- 待处理列表直接操作，无需跳转
- 最新操作动态时间线
- 销售顾问专属"我的待处理"和"我的已驳回"

### 📜 全链路审计留痕
- **每一步操作都有记录**：创建、更新、审批、驳回、借出、归还、验收
- 记录操作人、时间、旧值、新值、备注
- 审计日志可按对象类型、ID筛选查询
- 不是写在注释里的权限，是存在数据库里的证据

### ⚠️ 状态冲突处理
- 基于 `version` 字段的乐观锁机制
- 并发修改时明确提示"数据已被修改，请刷新后重试"
- 避免状态覆盖导致的"说不清"

### 🔔 站内通知机制
- 审批、驳回、验收、回查等关键节点自动通知相关人员
- 按角色智能推送（如借出申请自动通知所有经理）

## 🏗️ 技术栈

| 层级 | 技术 |

## 🚀 快速开始

### 1. 一键初始化

```bash
npm run init
```

这个命令会依次执行：
- `npm install` - 安装依赖
- `prisma generate` - 生成 Prisma 客户端
- `prisma migrate dev --name init` - 创建数据库表结构
- `npx ts-node prisma/seed.ts` - 初始化用户和样品基础数据
- `npx ts-node prisma/demo-data.ts` - 导入演示业务数据（待审批、已驳回、需回查等）

### 2. 启动服务

```bash
npm run dev
```

### 3. 访问系统

打开浏览器访问：**http://localhost:3000**

### 重置演示数据

如需重新生成完整的演示场景：

```bash
npm run demo
```

## 📖 业务流程

### 样品借出流程
```
销售创建申请 → 待经理审批 [可驳回] → 审批通过 → 确认样品已借出 → 借出中
                                 ↓
                             [驳回] → 结束
```

### 样品归还流程
```
销售提交归还 → 待验收 [可标记需回查] → 验收通过 → 完成
                               ↓
                           [需回查] → 重新验收
```

### 状态说明

| 借出状态 | 说明 |
|----------|------|
| `DRAFT` | 草稿（暂未使用） |
| `PENDING_APPROVAL` | 待审批 - 经理可操作 |
| `APPROVED` | 已批准 - 可确认借出 |
| `BORROWED` | 借出中 - 可申请归还 |
| `RETURNING` | 归还中 - 待验收 |
| `COMPLETED` | 已完成 |
| `REJECTED` | 已驳回 |

| 归还状态 | 说明 |
|----------|------|
| `PENDING_INSPECTION` | 待验收 |
| `INSPECTION_PASSED` | 验收通过 |
| `NEEDS_REVIEW` | 需回查 - 有损坏或缺失 |
| `COMPLETED` | 已完成 |

## 🔌 API 契约

所有接口前缀：`/api`，需要认证的接口需在 Header 中携带 `Authorization: Bearer <token>`

### 认证接口

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| POST | `/auth/login` | 登录获取 token | 公开 |
| GET | `/auth/me` | 获取当前用户信息 | 已登录 |

### 样品接口

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/samples` | 获取样品列表（支持 keyword/status/category 筛选） | 全部 |
| GET | `/samples/:id` | 获取样品详情 | 全部 |
| POST | `/samples` | 新增样品 | 经理 |
| PUT | `/samples/:id` | 更新样品 | 经理 |

### 借出接口

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/borrows` | 获取借出列表（支持 status/my 筛选） | 全部 |
| GET | `/borrows/:id` | 获取借出详情（含操作日志） | 全部 |
| POST | `/borrows` | 创建借出申请 | 销售/经理 |
| POST | `/borrows/:id/approve` | 审批通过 | 经理 |
| POST | `/borrows/:id/reject` | 审批驳回 | 经理 |
| POST | `/borrows/:id/confirm-borrow` | 确认样品已借出 | 全部 |
| POST | `/borrows/:id/return` | 提交归还 | 销售/经理 |

### 归还验收接口

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/returns` | 获取归还列表 | 经理/协调 |
| POST | `/returns/:id/inspect-pass` | 验收通过 | 经理/协调 |
| POST | `/returns/:id/need-review` | 标记需回查 | 经理 |
| POST | `/returns/:id/complete` | 完成归还流程 | 经理 |

### 公共接口

| 方法 | 路径 | 说明 | 权限 |
|------|------|------|------|
| GET | `/dashboard` | 首页看板数据 | 已登录 |
| GET | `/audit-logs` | 审计日志（支持 entityType/entityId 筛选） | 已登录 |
| GET | `/notifications` | 获取我的通知 | 已登录 |
| POST | `/notifications/:id/read` | 标记通知已读 | 已登录 |
| GET | `/health` | 健康检查 | 公开 |

### 响应格式

```json
{
  "code": 0,
  "message": "成功",
  "data": {}
}
```

- `code: 0` 表示成功
- `code: 401` 未认证
- `code: 403` 权限不足
- `code: 404` 资源不存在
- `code: 409` 状态冲突（版本不匹配）
- `code: 500` 服务器错误

## 🛡️ 设计要点说明

### 为什么用 version 字段？
在 `Sample`、`SampleBorrow`、`SampleReturn` 表中都有 `version` 字段，用于：
1. **并发控制**：多人同时操作同一条记录时，后提交的会被拒绝
2. **状态追溯**：每次状态变更版本号 +1，可回查变更历史
3. **扯皮防护**：谁改的、什么时候改的、改之前是什么样，审计日志里都有

### 为什么每个状态变更都要写审计日志？
售后纠纷最怕"说不清"。系统保证：
- 每一次状态流转都有操作人、时间、变更前后数据
- 审计日志一旦写入不可修改（业务层面）
- 可以按单条借出记录 ID 查出完整的操作时间线

### 为什么用站内通知而不是邮件/短信？
核心是**降低演示门槛**，但架构上可扩展：
- 通知表已经按用户维度存储
- 如需接入邮件/短信/企业微信，只需在 `createNotification` 函数后追加逻辑

## 🐛 常见问题

### 数据库报错？
删除 `prisma/dev.db` 和 `prisma/migrations` 目录，重新执行：
```bash
npm run prisma:migrate
npm run seed
```

### 端口被占用？
修改 `src/server.ts` 中的 `PORT` 变量，或启动时指定：
```bash
PORT=3001 npm run dev
```
