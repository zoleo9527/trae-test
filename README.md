# 高尔夫练习场 - 球道预约与教练排班管理系统

基于 **Go Fiber** + **SvelteKit** 构建的全链路可追踪高尔夫练习场管理系统。

---

## ✨ 核心特性

### 🔗 全链路追踪
将预约、签到、器材借还、储值扣减、签出、异常处理串联成一条完整可回溯的链条，点击任意预约即可查看完整上下文。

### 🎭 角色差异化视图
不同岗位看到不同的功能入口，避免信息干扰：

| 角色 | 可见功能 |
|------|---------|
| **前台 (reception)** | 今日概览、预约管理、器材管理、会员储值、异常处理 |
| **教练 (coach)** | 今日概览、预约管理、教练排班、异常处理 |
| **教练主管 (coach_manager)** | 全部功能，可编辑排班 |
| **场馆经理 (venue_manager)** | 全部功能，拥有最高权限 |

### 🚨 异常处理工作流
- 8 种异常类型：未到场、迟到、超时、支付问题、器材损坏、客户投诉、排班冲突、打位故障
- 三级优先级：高 / 中 / 低
- 完整状态流转：待处理 → 处理中 → 已解决 → 已关闭
- 支持跟进记录和自动退款/违约金处理

### 📝 全量操作留痕
所有关键操作自动记录 AuditLog，包含：
- 操作人、操作时间、IP 地址
- 操作类型和详细描述
- 变更前后的值对比

## 🚀 启动方式

### 方式一：一键启动（推荐）

```bash
# 安装所有依赖
npm run install:all

# 启动前后端开发服务器
npm run dev
```

### 方式二：分别启动

**后端服务** (端口 3000):
```bash
cd backend
go mod download
go run main.go
```

**前端服务** (端口 5173):
```bash
cd frontend
npm install
npm run dev
```

### 生产构建

```bash
npm run build
npm run start
```

## 🏗️ 技术架构

### 后端 (Go Fiber)
```
backend/
├── main.go                 # 应用入口
├── pkg/
│   ├── models/             # 数据模型 (12 个核心实体)
│   ├── database/           # 数据库 + 种子数据
│   ├── handlers/           # API 处理器
│   └── middleware/         # 认证 + 错误处理
```

**API 边界**：所有业务逻辑和金额计算都在后端完成，前端仅负责展示和交互。

### 前端 (SvelteKit)
```
frontend/
├── src/
│   ├── routes/             # 页面路由
│   │   ├── login/          # 登录页
│   │   └── (app)/          # 应用主视图
│   │       ├── +page.svelte        # 今日概览
│   │       ├── bookings/           # 预约管理
│   │       ├── schedule/           # 教练排班
│   │       ├── equipment/          # 器材管理
│   │       ├── members/            # 会员储值
│   │       └── exceptions/         # 异常处理
│   ├── lib/
│   │   ├── components/
│   │   │   └── ExceptionDrawer.svelte  # 核心异常抽屉
│   │   ├── api/              # API 客户端
│   │   ├── stores/           # 状态管理
│   │   └── types/            # TypeScript 类型
```

## ⚠️ 刻意简化的部分

为了保持演示项目的简洁，以下部分做了简化处理，生产环境需补充：

### 1. 认证安全
- 当前使用 Base64 编码的简单 token，生产应使用 JWT / Oauth2
- 密码明文存储，应使用 bcrypt / argon2 加盐哈希
- 缺少 token 过期和刷新机制

### 2. 权限控制
- 前端仅做菜单显示控制，后端仅统一校验登录
- 需完善接口级别的 RBAC 权限校验

### 3. 数据库
- 使用 SQLite 方便演示，生产建议 PostgreSQL / MySQL
- 缺少数据库连接池配置和慢查询优化

### 4. 业务逻辑
- 计费规则硬编码（超时 ¥5/分钟，违约金比例等），应做成可配置
- 缺少发票管理、财务对账功能
- 缺少真正的微信/支付宝支付集成

### 5. 运维部署
- 没有 Docker 容器化和 docker-compose
- 没有 CI/CD 流水线配置
- 缺少日志收集和监控告警

### 6. 交互细节
- 部分按钮（如新建排班、新增器材）仅 UI 占位，未实现完整流程
- 没有 WebSocket 实时通知
- 缺少数据导出功能

## 📁 前后端边界约定

✅ **后端负责**：
- 所有数据校验和业务规则
- 金额计算、余额更新、交易记录
- 异常状态流转和自动处理（退款、违约金）
- 操作留痕记录

✅ **前端负责**：
- 页面展示和用户交互
- 表单验证（仅即时体验）
- 路由和状态管理
- 响应式布局

❌ **禁止**：
- 前端直接计算金额
- 前端直接修改数据库状态
- 业务逻辑散落在页面代码中

6. 切换到「操作留痕」标签页，可看到完整的操作时间线
7. 切换到「储值记录」标签页，可看到违约金扣减记录

系统已自动将所有相关信息串联，无需在多个页面间跳转查找。
