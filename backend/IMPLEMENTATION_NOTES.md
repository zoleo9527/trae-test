# 钟表售后-配件申请与库存锁定系统

## 一、系统概述

本系统为钟表售后维修业务提供完整的配件申请与库存锁定管理解决方案，解决了传统方式下寄修登记表、配件库存、客户回执分散管理导致的数据不一致、信息核对繁琐、配件锁定失误、维修进度口径不一等核心痛点。

### 系统定位
- **后端重**：完整的API契约、状态流转校验、异常处理、证据链追踪
- **前端轻**：后端能力完备，前端仅需关注交互体验
- **权限清**：角色边界清晰，各角色仅看到和处理自己权责范围内的工作

---

## 二、核心设计理念

### 1. 接力感设计
各角色进入系统后清晰知道自己要处理的任务：
- **接件顾问**：看到待报价、待确认报价、待取件通知的寄修单
- **维修技师**：看到分配给自己的维修任务、待领取的配件申请
- **售后经理**：看到待审批的配件申请、库存预警、异常订单

### 2. 证据链完整
所有操作均可回溯：
- 状态变更历史（谁在什么时间因为什么原因改了什么状态）
- 操作日志（全链路Trace ID追踪）
- 备注系统（驳回原因、补录说明、客户回复、内部沟通都在一个地方）

### 3. 异常前置
- 状态流转严格校验，非法操作直接拦截
- 库存锁定自动处理，防止超卖
- 幂等性支持，防止重复提交
- 异常操作日志单独归类，支持快速回查

## 四、权限与角色设计

### 角色定义

| 角色 | 职责 | 典型用户 | 核心权限 |
|------|------|----------|----------|
| **ADMIN** | 系统管理员 | 运维/IT | 全部权限、用户管理、系统配置 |
| **SERVICE_MANAGER** | 售后经理 | 售后主管 | 审批申请、管理库存、查看全部数据、导出报表 |
| **RECEPTIONIST** | 接件顾问 | 前台接待 | 创建寄修单、与客户沟通、提交配件申请 |
| **TECHNICIAN** | 维修技师 | 维修师傅 | 查看维修任务、创建配件申请、领取配件 |

### 权限边界设计考量
- **最小权限原则**：每个角色默认只分配必要权限
- **操作隔离**：创建者只能编辑自己创建的草稿单
- **审批分离**：创建申请和审批申请必须是不同角色
- **数据隔离**：列表查询可根据角色自动过滤数据范围（当前实现全量数据，可在下一步增强）

## 五、核心业务流程

### 1. 寄修单生命周期

```
PENDING_QUOTATION (待报价)
    → QUOTATION_SENT (已报价)
        → QUOTATION_APPROVED (客户确认)
            → AWAITING_PARTS (待配件)
                → IN_REPAIR (维修中)
                    → REPAIR_COMPLETED (维修完成)
                        → READY_FOR_PICKUP (待取件)
                            → PICKED_UP (已取件)
                                → CLOSED (已结案)
        → QUOTATION_REJECTED (客户拒绝)
            → QUOTATION_SENT (重新报价) 或 → CLOSED
            任一环节 → CANCELLED (取消)
```

### 2. 配件申请接力流程

```
DRAFT (草稿: 技师/顾问创建)
    ↓ [提交]
PENDING_APPROVAL (待审批: 售后经理审批)
    ↓ [批准]            ↓ [驳回]
APPROVED (已批准)      REJECTED (已驳回)
    ↓ [锁定库存]           ↓ [补录]
PROCESSING (处理中)     PENDING_APPROVAL (重新审批)
    ↓ [发放/领取]
COMPLETED (已完成)

    任一环节 → CANCELLED (取消)
```

### 3. 库存锁定机制

**三种锁定状态**：
- `ACTIVE`：锁定中，库存已预留
- `RELEASED`：已释放，库存退回
- `CONSUMED`：已消耗，实际出库
- `EXPIRED`：已过期，定时任务清理

**锁定流程**：
1. 配件申请批准时，自动检查可用库存
2. 可用数量 ≥ 申请数量：全额锁定，状态变APPROVED
3. 可用数量 < 申请数量：部分锁定，状态变PARTIAL_APPROVED
4. 可用数量 = 0：不锁定，状态变AWAITING_STOCK
5. 实际领取时：CONSUMED锁定，扣减实际库存

## 六、实现取舍点

### 1. 数据库选型
- **当前选择**：SQLite
- **原因**：零依赖、开箱即用、便于演示和测试
- **代价**：不支持高并发、不支持某些高级特性（如某些JSON操作）
- **迁移方案**：Prisma支持切换为PostgreSQL/MySQL，仅需修改DATABASE_URL和prisma migrate

### 2. 权限粒度
- **当前选择**：角色 + 权限列表双层校验
- **原因**：满足当前业务需求，不引入复杂的RBAC模型
- **可扩展**：后续可增加`RolePermission`表实现动态权限配置

### 3. 库存模型
- **当前选择**：单仓简单库存，批次可选
- **原因**：当前业务场景单仓库即可满足
- **可扩展**：支持多仓库、多批次、先进先出等复杂库存策略

### 4. 状态流转校验
- **当前选择**：代码中硬编码状态转移矩阵
- **原因**：简单直接，性能好，编译时校验
- **代价**：修改状态流转需要改代码
- **可扩展**：后续可将状态机配置化存入数据库

### 5. 操作日志
- **当前选择**：中间件统一采集，所有请求都记录
- **原因**：操作审计、问题回查的基础
- **代价**：日志量较大，对数据库写入有压力
- **可扩展**：后续可异步写入、定期归档、接入ELK

### 6. 幂等性
- **当前选择**：基于`X-Idempotency-Key`请求头实现
- **原因**：可选使用，不强制，对性能影响小
- **可扩展**：后续可对关键接口强制要求幂等键

## 八、API概览

### 认证模块
- `POST /api/v1/auth/login` - 用户登录
- `GET /api/v1/auth/me` - 获取当前用户
- `POST /api/v1/auth/change-password` - 修改密码

### 寄修单管理
- `GET /api/v1/repair-orders` - 列表查询（分页+多条件筛选）
- `GET /api/v1/repair-orders/:id` - 详情（含完整证据链）
- `POST /api/v1/repair-orders` - 创建寄修单
- `PATCH /api/v1/repair-orders/:id/status` - 状态变更
- `POST /api/v1/repair-orders/:id/quotation` - 提交报价
- `POST /api/v1/repair-orders/:id/confirm-quotation` - 客户确认报价
- `POST /api/v1/repair-orders/:id/satisfaction` - 提交满意度
- `POST /api/v1/repair-orders/:id/notes` - 添加备注

### 配件与库存
- `GET /api/v1/parts` - 配件列表
- `POST /api/v1/parts` - 创建配件
- `GET /api/v1/inventories` - 库存列表（支持低库存筛选）
- `GET /api/v1/inventories/:id` - 库存详情（含锁定信息）
- `POST /api/v1/inventory-locks` - 锁定库存
- `POST /api/v1/inventory-locks/:id/release` - 释放锁定
- `POST /api/v1/inventory-locks/:id/consume` - 消耗锁定（出库）
- `POST /api/v1/inventory-locks/cleanup-expired` - 清理过期锁定

### 配件申请（核心）
- `GET /api/v1/part-applications/pending-approvals` - 我待审批的
- `GET /api/v1/part-applications` - 列表查询
- `GET /api/v1/part-applications/:id` - 详情（含证据链）
- `POST /api/v1/part-applications` - 创建申请（草稿）
- `POST /api/v1/part-applications/:id/submit` - 提交审批
- `POST /api/v1/part-applications/:id/approve` - 审批通过（自动锁库存）
- `POST /api/v1/part-applications/:id/reject` - 驳回（必须填原因）
- `POST /api/v1/part-applications/:id/supplement` - 补录并重提交
- `POST /api/v1/part-applications/:id/pickup` - 配件发放（自动消耗库存）

### 通用查询
- `GET /api/v1/dashboard/stats` - 仪表板统计
- `GET /api/v1/export?type=xxx&format=csv` - 数据导出
- `GET /api/v1/operation-logs` - 操作日志
- `GET /api/v1/operation-logs/errors` - 异常日志
- `GET /api/v1/trace/:traceId` - 全链路追踪

## 十二、关键设计决策回顾

### 为什么选择 Express + Prisma？
1. **Express**：轻量、灵活、学习成本低，Node.js生态最成熟的Web框架
2. **Prisma**：
   - 类型安全的数据库访问，编译时就能发现很多问题
   - Schema驱动，自动生成迁移和类型定义
   - 支持多种数据库，便于后续升级
   - 开发体验好，查询API直观

### 为什么状态流转要硬编码校验？
1. **可靠性**：业务规则必须强制执行，不能靠前端约束
2. **性能**：不需要查数据库就能判断合法性
3. **可预测**：所有合法状态转移在代码中一目了然
4. **可测试**：可以为状态机编写单独的单元测试

### 为什么操作日志要用中间件统一采集？
1. **避免遗忘**：业务开发不需要关心日志，默认就会记录
2. **一致性**：所有日志格式统一，便于分析和查询
3. **完整度高**：能捕获到鉴权失败等业务代码之前的错误
4. **Trace ID**：可以串联起整个请求链路

### 为什么备注要单独建模，而不是加个字段？
1. **类型区分**：驳回原因、补录说明、客户回复是不同性质的信息
2. **时间线**：每条备注有创建人和时间，形成完整的沟通记录
3. **查询方便**：可以单独查询某类备注，比如"所有驳回原因"
4. **扩展友好**：后续可以加附件、@提及等功能
